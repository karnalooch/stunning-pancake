## Faza 1 — Routing & Navigation Integrity (wysoki priorytet, implementacja TERAZ)

Wykrywa martwe linki, brakujące trasy, ekrany-widma. Bez serwera, < 5s runtime.

| # | Nazwa | Plik | Co wykrywa |
|---|-------|------|-----------|
| 1 | **Route Parity Check** | `scripts/audit-routes.ts` | Sidebar `NAV_SECTIONS` paths vs `<Route path="...">` in `App.tsx`. ERROR: sidebar link without route. WARNING: route without sidebar entry. |
| 2 | **Dead Screen Detection** | `scripts/audit-screens.ts` | Pliki `.tsx` w `admin/src/modules/` niezaimportowane w żadnym innym pliku w projekcie. |
| 3 | **Navigation Smoke Test** | `admin/e2e/navigation-smoke.spec.ts` | Playwright E2E — klika każdy `data-testid="nav-*"` w sidebarze, asercja: brak "404" / "not found" / "Access Denied" / crash strony. |
| 4 | **Route Liveness Probe** | `admin/e2e/routing-registry.spec.ts` | Playwright E2E — odwiedza bezpośrednio każdy URL z `NAV_SECTIONS`, asercja: strona się renderuje bez błędu. |
| 5 | **Mobile Screen Parity** | `scripts/audit-mobile-routes.ts` | Pliki w `mobile/src/screens/` vs plan `plans/screen-architecture-plan.md`. Wykrywa: brakujący ekran z planu, ekran bez wpisu w planie. |
| 6 | **API Gap Analysis** | `scripts/audit-api-gaps.ts` | Parsuje `apiClient.get/post/...` w frontendzie, porównuje z `urlpatterns` w Django i widokami DRF. Wykrywa: frontend woła endpoint bez backendu, backend ma endpoint bez frontendowego konsumenta. |
| 7 | **RBAC-Permission Consistency Audit** | `scripts/audit-rbac.ts` | Porównuje `roles[]` w `NAV_SECTIONS` (Layout.tsx) z `permissions[]` w `<PermissionGuard>` dla tej samej trasy (App.tsx). ERROR: rola w sidebarze, ale brak trasy dla tej roli. WARNING: PermissionGuard używa uprawnienia, które nie istnieje w Django. |
| 8 | **Redirect Chain Audit** | `scripts/audit-redirects.ts` | Analizuje wszystkie `<Navigate to="...">` w `App.tsx` i wykrywa: redirect loops (A → B → A), redirecty do nieistniejących tras, kaskadowe przekierowania (>2). |

## Integracja z CI (ci.yml)

```yaml
# Nowy job: AUDIT — wszystkie static audyty (Faza 1 + 2 + 3)
audit:
  name: Audit (Route + Code + Security)
  runs-on: ubuntu-latest
  needs: [backend, admin]
  steps:
    - uses: actions/checkout@v6
    - uses: actions/setup-node@v6
      with:
        node-version: '20'
        cache: npm
        cache-dependency-path: admin/package-lock.json
    - run: cd admin && npm ci
    - run: cd admin && npm run audit:all   # wszystkie skrypty z Faza 1-3

# E2E Navigation Smoke — rozszerza istniejący job e2e o nowe testy
e2e:
  # ...istniejący setup...
  - run: cd admin && npx playwright test   # obejmuje nav smoke + route liveness
```

## 🔴 Błędy krytyczne do natychmiastowej naprawy

### A. 5 dead sidebar linków — brakujące `<Route>` w App.tsx

| Link w sidebarze | Problem | Proponowana naprawa |
|-----------------|---------|-------------------|
| `/owner/departments` (Działy) | Komponent `Departments.tsx` istnieje ale nie ma trasy | Dodać `<Route path="departments" element={<Departments />} />` pod `/owner` |
| `/owner/analytics/events` (Events) | Komponent `EventsManager.tsx` istnieje, brak trasy | Dodać `analytics/` subgroup w `/owner` lub przenieść do Dashboard jako subkomponent |
| `/owner/analytics/sponsorship` | `SponsorshipAnalytics.tsx` istnieje, brak trasy | j.w. |
| `/owner/analytics/vouchers` | `RewardsVouchers.tsx` istnieje, brak trasy | j.w. |
| `/owner/analytics/feedback` | `BetaFeedback.tsx` istnieje, brak trasy | j.w. |

**Decyzja architektoniczna do podjęcia:** Czy analytics mają być:
- **Opcja 1:** Osobne trasy (każda z własnym URL, jak sugeruje sidebar) — potrzeba 4 nowych `<Route>` w App.tsx  
- **Opcja 2:** Subkomponenty w Dashboard (tak jak GlobalHeatmap, SystemIntelligence już są wbudowane) — usunąć z sidebaru i wkomponować w Dashboard

**Rekomendacja:** Opcja 1 — osobne trasy. Cleaner, skalowalne, sidebar już to sugeruje.

### B. 4 RBAC inconsistencies — użytkownicy dostają 403 po kliknięciu

| Trasa | Rola sidebar | Permisje route | Problem |
|-------|-------------|----------------|---------|
| `/owner/white-label` | TENANT_MODERATOR ✅ | `users.edit` | TENANT_MODERATOR nie ma `users.edit` w ROLE_PERMISSIONS |
| `/owner/anti-cheat` | TENANT_ADMIN ✅ | `activities.approve` | TENANT_ADMIN nie ma `activities.approve` |
| `/owner/sponsor` | TENANT_ADMIN ✅ | `poi.view, vouchers.view` | TENANT_ADMIN nie ma tych permisji |
| `/owner/sponsor` | TENANT_MODERATOR ✅ | `poi.view, vouchers.view` | TEANT_MODERATOR nie ma tych permisji |

**Proponowana naprawa:**

*Opcja A — Dostosować role sidebar (usuwać role, które nie mają dostępu):*
- WhiteLabel: usunąć TENANT_MODERATOR z roles
- AntiCheat: usunąć TENANT_ADMIN z roles (zostawić tylko GLOBAL_OWNER + TENANT_MODERATOR)
- Sponsor: usunąć TENANT_ADMIN + TENANT_MODERATOR z roles (zostawić GLOBAL_OWNER + SPONSOR)

*Opcja B — Dodać brakujące permisje do ról (rozszerzyć dostęp):*
- TENANT_ADMIN: dodać `activities.approve`, `poi.view`, `vouchers.view`
- TENANT_MODERATOR: dodać `users.edit`, `poi.view`, `vouchers.view`

**Rekomendacja:** Opcja A (restrykcyjna) — mniej dostępów = mniej powierzchni ataku. Nie dawać uprawnień, których rola nie potrzebuje.

### C. Duplikat catch-all `*` w App.tsx

W `App.tsx:59` i `App.tsx:125` są dwie trasy `<Route path="*" ...>`:
- Pierwsza (niezalogowany): przekierowuje do `/login`
- Druga (zalogowany): przekierowuje do `/owner/dashboard`

To nie jest funkcjonalny bug (są w osobnych gałęziach `isAuthenticated`), ale `audit-redirects.ts` tego nie rozróżnia.  
**Naprawa:** Wyłączyć to ostrzeżenie w audycie dla tego konkretnego przypadku (aware of auth branching).
