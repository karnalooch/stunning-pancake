## 1. Preamble

The **4VELO** platform is an open-source, self-hosted ecosystem for endurance sports - from amateur training to professional competitions. It combines GPS activity tracking, gamification, anti-cheat system and advanced analytics in one coherent environment.

This Constitution defines immutable rules that apply to all project contributors - from developers to DevOps to UX designers. Every architectural decision, every pull request and every implementation must comply with the spirit and letter of this document.

### Scope of validity

| Area | Valid |
|---|---|
| Source code (backend, frontend, mobile) | ✅ |
| Infrastructure (Docker, CI/CD, Railway) | ✅ |
| Technical and operational documentation | ✅ |
| Code review and deployment processes | ✅ |
| Data management and security | ✅ |

## 2. Fundamental Principles

Five pillars on which the 4VELO platform is based. No compromise is allowed in these areas.

### 2.1 Security First

- All data at rest is **encrypted** (AES-256, Fernet for OAuth tokens)
- All communication forced via **HTTPS** - HSTS with `max-age=31536000`
- **RBAC** (Role-Based Access Control) mandatory for every API endpoint
- All secrets stored in environment variables (Railway Variables / `.env`)
- We **Never** commit secrets to the repository

### 2.2 Privacy by Design

- **Row-Level Security (RLS)** at the database level - each tenant only sees his own data
- **Privacy Zones** - masking GPS coordinates in user private zones
- Full compliance with **GDPR**:
  - The right to be forgotten (hard delete + anonymization)
  - Right to transfer data (JSON/GPX export)
  - Transparent privacy and user consent policy

### 2.3 Performance

| Metrics | Purpose | Measurement |
|---|---|---|
| FPS in mobile HUD | **60 FPS** | React Native Skia GPU profiling |
| API response time | **< 200 ms** (p95) | Prometheus + Grafana |
| Availability (uptime) | **99.9%** | Health checks every 30s |
| SPA charging time | **< 3 s** (First Contentful Paint) | Lighthouse CI |

### 2.4 Fair Play

- **4-layer Anti-Cheat system:**
  1. GPS signal validation (speed, acceleration, interpolation)
  2. Statistical analysis (outliers, seasonal anomalies)
  3. Machine learning (anomaly detection - Isolation Forest, LSTM)
  4. Human moderation (moderator dashboard)
- **Zero tolerance** for cheating - detected violations result in a permanent ban
- All Anti-Cheat decisions are **auditable** and provided with a reason

### 2.5 Open Standards

- **REST API** compliant with RESTful conventions
- **OGC Moving Features** - open standard for motion data
- **OpenAPI 3.1** - API documentation auto-generated by `drf-spectacular`
- Preference for open formats: **GPX**, **GeoJSON**, **CSV**

## 3. Architecture Rules

### 3.1 Backend - Django + DRF + PostGIS

| Rule | Description |
|---|---|
| **ORM-first** | We never bypass Django's ORM for write operations. Raw SQL only for read optimization (materialized views) |
| **DRF serializers** | Each API endpoint has a defined serializer - no manual building of JSON |
| **PostGIS** | All geospatial queries via GeoDjango ORM (`gis` module) |
| **Celery** | Long-running operations (GPX processing, ML retraining) always in asynchronous tasks |
| **Tests** | Each new endpoint must have integration tests (`APITestCase`) |

### 3.2 Frontend (Admin) - React + Mantine + Vite| Rule | Description |
|---|---|
| **TypeScript mandatory** | All frontend code in TypeScript, strict mode |
| **Mantine v7** | UI components exclusively from Mantine - no mixing of libraries |
| **Vite** | Build toolchain via Vite, configuration in `vite.config.ts` |
| **Condition** | React Context for auth, local component state for UI |

### 3.3 Mobile - React Native + Expo

| Rule | Description |
|---|---|
| **Expo managed workflow** | Preferred managed workflow Expo, dev-client for native modules |
| **Skia GPU** | HUD layer rendered by `@shopify/react-native-skia` at 60 FPS |
| **Legend-State** | State management by Legend-State (observable, efficient) |
| **GPS** | `expo-location` with configurable accuracy and battery saving |

### 3.4 Database - PostgreSQL + PostGIS + TimescaleDB

| Rule | Description |
|---|---|
| **RLS mandatory** | Each multi-tenant table has Row-Level Security | enabled
| **TimescaleDB** | Telemetry data (GPS, sensors) as hypertables with automatic compression |
| **Materialized views** | City rankings, aggregations - refresh by Celery Beat |
| **Indexes** | GiST indexes for geospatial columns, B-tree for foreign keys |

### 3.5 Cache - Redis

| Application | Key |
|---|---|
| User sessions | `session:<user_id>` |
| Rankings (leaderboards) | `leaderboard:<city_id>:<segment_id>` |
| Celery Broker | Queues `celery`, `high_priority`, `low_priority` |
| API query cache | `api:<endpoint_hash>:<params_hash>` (TTL 60s) |

## 4. Safety Standards

### 4.1 Authentication

| Mechanism | Details |
|---|---|
| **JWT Access Token** | 60 minutes validity, signed RS256 |
| **JWT Refresh Token** | 7 days validity, rotation + blacklisting when logging out |
| **Token blacklist** | Redis `blacklist:<jti>` with TTL = token expiration time |
| **Rate limiting** | 5 login attempts / minute / IP, blocked for 15 minutes after exceeding |

### 4.2 Authorization

- **RBAC** with 28 granular permissions (e.g. `activities.view_activity`, `users.manage_roles`)
- **5 system roles:**

| Role | Description |
|---|---|
| `admin` | Full access to the system, tenant management |
| `moderator` | Activity moderation, Anti-Cheat flag management |
| `tenant_admin` | Tenant and user management within tenant |
| `sponsor` | Access to sponsored heatmaps, campaign analytics |
| `user` | Basic End User Permissions |

- All administrative actions are **logged** with the user context

### 4.3 Encryption

| Data | Method |
|---|---|
| OAuth tokens (Strava, Garmin) | Fernet (symmetric encryption) in database |
| User passwords | Django `make_password()` (PBKDF2 + SHA-256) |
| Communication | TLS 1.3, HSTS |
| Database backups | AES-256 encrypted before transfer |

### 4.4 Audit

- All admin actions logged in `AuditLog`
- **Impersonation Tracked** - Each impersonation session has its own audit entry
- Non-removable audit logs (append-only)

### 4.5 Secrets

- **We never commit** secrets to the repository
- We use **Railway Variables** (production) or `.env` file (development)
- The `.env.example` file contains a template without production values
- Secret rotation every 90 days

## 6. Documentation Policy

### 6.1 Code documentation

| Element | Requirement |
|---|---|
| Public functions/methods | Docstring (Google-style for Python, JSDoc for TypeScript) |
| Complex logic | Comment explaining "why", not "what" |
| Magic constants | Named constants with comment |
| Workarounds | Marked with `// FIXME:` or `// HACK:` with date and reason |

### 6.2 API Documentation

- **OpenAPI 3.1** auto-generated by `drf-spectacular`
- Available under `/api/docs/` (Swagger UI) and `/api/redoc/` (ReDoc)
- Each endpoint has: description, parameters, sample request/response, error codes

### 6.3 Architectural Decisions (ADR)

- All important architectural decisions recorded in [`docs/adr/`](../adr/)
- Format: [Michael Nygard ADR](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)
- Sequential numbering: `adr/0001-decision-name.md`

### 6.4 User Documentation

- **In Polish** (end users are mainly Polish-speaking athletes)
- Key documents:
  - [GETTING_STARTED.md](GETTING_STARTED.md) - getting started
  - [INSTALLATION.md](INSTALLATION.md) - installation and configuration
  - [TROUBLESHOOTING.md](TROUBLESHOOTING.md) - Troubleshooting

### 6.5 Up-to-date documentation

- **Any change in functionality requires updating the documentation**
- Documentation review every sprint (at least once every 2 weeks)
- Links inside the documentation checked automatically (CI check)

## 7. Implementation Rules

### 7.1 `main` branch

| Rule | Description |
|---|---|
| **Ready for production** | `main` always contains code that can be safely deployed |
| **All tests must pass** | CI blocks merge if any test fails |
| **Linear history** | Preferred squash merge for readability |
| **Protected branch** | `main` protected - requires PR and review |

### 7.2 Zero-Downtime Deployments

- **Additive migrations** - new columns with default values, removing old columns in the next version
- **Feature flags** for breaking changes
- **Rolling updates** in Railway / Docker Swarm - gradual replacement of containers
- Health check of the `/api/infra/health/` endpoint before redirecting traffic

### 7.3 Rollback Plan

Each implementation must have a **documented and tested** rollback plan:

1. Migration rollback script (if applicable)
2. Possibility to restore the previous version of the container
3. Feature flag to disable the new functionality
4. Estimated rollback time (target < 5 minutes)

### 7.4 Health Checks

| Endpoint | Description | Expected status |
|---|---|---|
| `/api/infra/health/` | Overall application status | `200 OK` with `{"status": "healthy"}` |
| `/api/infra/health/db/` | Connecting to the database | `200 OK` |
| `/api/infra/health/redis/` | Connecting to Redis | `200 OK` |
| `/api/infra/health/celery/` | Celery workers status | `200 OK` |

### 7.5 Monitoring

| Tool | Application |
|---|---|
| **Sentry** | Backend and frontend bug tracking |
| **Health endpoints** | Uptime monitoring (UptimeRobot / BetterStack) |
| **Prometheus + Grafana** | Application metrics (optional, self-hosted) |
| **Railway logs** | Container logs in production |

## 8. Data Management

### 8.1 Backups (Backups)

| Element | Frequency | Retention |
|---|---|---|
| PostgreSQL (full backup) | Daily (02:00 UTC) | 30 days |
| PostgreSQL (WAL archiving) | Continuous | 7 days |
| Redis (RDB dump) | Every day | 7 days |
| User files (media) | Every day | 30 days |

- **Recovery procedure tested once a month**
- AES-256 encrypted backups before transfer to storage

### 8.2 Data Retention Policy| Data type | Storage period |
|---|---|
| Activities (rides, training) | **Account lifespan + 1 year** after deletion |
| Raw telemetry (GPS points) | **Anonymized after 90 days** (aggregated statistics only) |
| User account details | Until the account is deleted + 30 days (grace period) |
| Audit logs | **Minimum 3 years** (GDPR requirement) |
| Application logs | 30 days (rotated) |

### 8.3 GDPR/GDPR Compliance

| User rights | Implementation |
|---|---|
| **Right to delete** | Endpoint `/api/users/me/delete/` - hard delete + aggregate data anonymization |
| **Right to transfer** | Export all data in JSON + GPX format (`/api/users/me/export/`) |
| **Right to access** | Endpoint `/api/users/me/data/` - full view of stored data |
| **Right to rectification** | Profile editing, ability to correct activity data |
| **Privacy Zones** | The user defines zones (geofence) where GPS is masked |

### 8.4 Production data in development

- **We never copy the production database to development environments**
- We use **seed data** (`python manage.py seed_data`) for realistic test data
- Alternatively: anonymized production snapshots (all PII removed)

## 9. Incident Response

### 9.1 Criticality Levels (Severity)

| Level | Definition | Example |
|---|---|---|
| **P0** - Critical | Complete unavailability of the platform | Offline database, 500 on all endpoints |
| **P1** - High | Key functionality unavailable | Can't record activity, login doesn't work |
| **P2** - Medium | Performance degradation or partial unavailability | Leaderboards do not load, delays > 5s |
| **P3** - Low | Minor faults | Cosmetic error, typo in UI |

### 9.2 Response Times

| Level | Response time | Repair time (target) |
|---|---|---|
| **P0** | **1 hour** | 4 hours |
| **P1** | **4 hours** | 24 hours |
| **P2** | **24 hours** | Next sprint |
| **P3** | Next sprint | Next release |

### 9.3 Post-Mortem

- **Each P0 and P1 incident requires a written post-mortem**
- Post-mortem format:
  1. **Timeline** - what happened, step by step
  2. **Root Cause** - Why the incident occurred
  3. **Impact** - How many users affected, duration
  4. **Corrective Action** - What was done to restore operation
  5. **Preventive actions** - what to change to prevent the incident from happening again
  6. **Lessons learned** - conclusions for the future
- Post-mortem stored in [`docs/runbooks/postmortems/`](runbooks/)

### 9.4 Runbooks

All common incidents must have a **runbook** in [`docs/runbooks/`](runbooks/):

| Runbook | Description |
|---|---|
| [db_recovery.md](runbooks/db_recovery.md) | Database unavailable |
| `redis-outage.md` | Redis/cache unavailable |
| [celery-backlog.md](runbooks/celery-backlog.md) | Celery queues are growing |
| `high-cpu.md` | High CPU usage |
| `ssl-expiry.md` | Expiring SSL certificate |
| `data-breach.md` | Suspected data leak |

## 10. Versioning

### 10.1 Semantic Versioning (SemVer)```
MAJOR.MINOR.PATCH
```| Version | Incremented when |
|---|---|
| **MAJOR** | Incompatible API changes, removal of functionality |
| **MINOR** | New functionality, backward compatible |
| **PATCH** | Bug fixes, backwards compatible |

- Current version: **v0.2.0-rc.1** (release candidate)
- Version `0.y.z` means the development phase before v1.0.0

### 10.2 API versioning

- **URL-based versioning:** `/api/v1/`, `/api/v2/`
- New API versions introduced with MAJOR changes
- Old API versions supported for a minimum of **6 months** after the new one is introduced

### 10.3 CHANGELOG

- Maintained in [Keep a Changelog](https://keepachangelog.com/) format
- File: [`CHANGELOG.md`](../../CHANGELOG.md)
- Updated with **every release**
- Categories: `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`

### 10.4 Deprecation Policy

| Element | Expiration period |
|---|---|
| API functions / endpoints | **6 months** from being marked as deprecated |
| Fields in models | 2 releases MINOR, then removal in MAJOR |
| Configuration (env vars) | 3 months from being marked as deprecated |

- All deprecations are **marked in the code** with the annotation `@deprecated` / `DeprecationWarning`
- Information about depreciation appears in **CHANGELOG** and **release notes**
- API users informed by `Sunset` header in HTTP responses
